# Архитектура ZapretForAndroid

Документ описывает, как устроено приложение и почему принято именно такое решение.
Читается вместе с `README.md`; здесь — только техника.

---

## 1. Почему userspace-стек

Задача — передать TLS ClientHello так, чтобы DPI-фильтр не смог сопоставить
SNI с блокируемым доменом, но сервер при этом увидел корректный поток.

На десктопе `zapret` решает это через `NFQUEUE`/`divert`: пакет перехватывается
**после** формирования ядром, правится (TTL, seq, фрагментация, опции) и
отправляется дальше. На Android без root такой возможности нет — `VpnService`
отдаёт приложению TUN-устройство, куда приходят IP-пакеты **от** локальных
приложений, а обратно приложение обязано вернуть целый корректный поток.

Значит, единственный доступный уровень управления — **граница записи в сокет**.
Чтобы её контролировать, нужно владеть клиентской стороной TCP. Отсюда решение:

> Приложение реализует TCP/IP-стек в userspace. Оно отвечает клиенту на SYN,
> ведёт собственное рукопожатие, принимает байты и **само** открывает настоящее
> соединение наружу через защищённый (`protect()`) сокет.

Побочный бонус: мы видим байты до TLS-шифрования потока как целого и можем
разобрать ClientHello, чтобы найти SNI и его границы.

## 2. Поток данных

```
приложение ──► TUN fd ──► ZapretVpnService.handlePacket
                                  │
                    ┌─────────────┼──────────────┐
                    ▼             ▼              ▼
                parseIp        proto=UDP      proto=TCP
                    │             │              │
                    │        port 53? ──► DnsHandler ──► DnsResolver
                    │             │              (hosts → кэш → DoH/DoT/system)
                    │             ▼
                    │        UdpStack (релей / блок QUIC / блок всего)
                    ▼
                 TcpStack ──► TcpConnection (на каждый поток)
                                  │
                                  ├─ SYN ──► рукопожатие, MSS-кламп, wscale
                                  ├─ данные ──► StrategyResolver ──► DesyncEngine
                                  │                                    │
                                  └─ protect()ed java.net.Socket ◄─────┘
```

### 2.1 ZapretVpnService

- Адрес туннеля `10.211.0.1/32`, маршрут `0.0.0.0/0`, DNS `10.211.0.2`.
  Использовать адрес туннеля как DNS нельзя: ядро отвечает на него локально,
  поэтому введён отдельный виртуальный адрес.
- IPv6: `fd61:7a6f:ee7::1/128`, `::/0`, DNS `fd61:7a6f:ee7::2`. Обёрнуто в
  try/catch — часть прошивок IPv6 в VPN не поддерживает.
- `setBlocking(true)`: читающий поток один, неблокирующий режим дал бы
  busy-wait и посадил бы батарею.
- Область действия: `ALL`/`EXCLUDE` → `addDisallowedApplication` (свой пакет
  добавляется всегда), `INCLUDE` → только `addAllowedApplication`. Смешивать
  allowed- и disallowed-списки нельзя; собственный пакет в allowed не
  добавляется — защита от петли обеспечивается `protect()`.
- Foreground-уведомление с типом `specialUse` (Android 14+), каналы
  `zapret_status` (LOW) и `zapret_events` (DEFAULT).

### 2.2 Горячая перезагрузка

Пересоздание `VpnService.Builder` требуется только для MTU, адресов, области
приложений и профиля. `signature(cfg)` считается по этим полям; если она
изменилась — `restart()`: `teardown()` гасит scope и обнуляет `instance`,
затем на `AppGraph.scope` через 200 мс запускается новый сервис. Все
остальные настройки читаются из `ConfigRepository.current` (`@Volatile`)
на каждый пакет и подхватываются без разрыва соединений.

## 3. TCP-стек (`core/stack/`)

### 3.1 TcpConnection

Состояния: `SYN_RECEIVED → ESTABLISHED → (FIN/RST)`.

- **Рукопожатие.** SYN-ACK с `wscale = 7`, полем окна 65535 (~8 МБ реально).
  wscale клиента запоминается; его окно пересчитывается и зажимается в 1 КБ–8 МБ.
- **MSS.** `mss = min(syn.mss, cfg.mssClamp, mtu - (20|40) - 20 - (12 если TS))`, минимум 536.
- **Отправка клиенту.** `ArrayDeque<Chunk>` + `unacked` + `inflight`.
  `maybeSend()` ограничен и окном клиента (`clientWindow - inflight`), и
  `MAX_INFLIGHT = 512 КБ`. Чтение из upstream приостанавливается, пока
  `queuedBytes > sendBufferKb * 1024`.
- **Ретрансмиссии.** Go-back-N, RTO 800 мс → 16 с (удвоение), `MAX_RETRANSMITS = 9`,
  fast retransmit по трём dup-ACK.
- **Приём от клиента.** `inboundBytes: AtomicInteger`, лимит 1 МБ. При превышении
  пакет не буферизуется, отправляется только ACK, а `advertiseWindow()` возвращает 0
  (zero window) — клиент сам притормозит. Счётчик `TrafficStats.dropped()`.
- **Первый блок.** До установления upstream-соединения клиентские данные копятся
  в буфере, ограниченном `MAX_INITIAL_BLOCK = 32 КБ` — этого хватает на ClientHello.
- **Upstream.** `Socket()` → `protect()` → `TCP_NODELAY` →
  (`wssize` ? `receiveBufferSize = wssizeWindow` : 256 КБ) →
  `connect(upstreamAddr, port, connectTimeoutMs)`. После передачи
  `wssizePackets * mss` байт буфер восстанавливается до 512 КБ.
- `upstreamAddr` для TCP/53 подменяется на реальный резолвер
  (`stack.dnsRedirectTarget()`), иначе DNS-запрос уйдёт в наш же перехват.

### 3.2 Реализация `--wssize`

`zapret` делает это, занижая окно в SYN-ACK, чтобы сервер дробил ServerHello.
У нас SYN-ACK синтезируется самим стеком, поэтому доступен и второй рычаг:
маленький `SO_RCVBUF` на upstream-сокете **до** `connect()` — ядро объявит
серверу узкое окно. После первых `wssizePackets` сегментов буфер
восстанавливается, иначе соединение задохнётся.

## 4. Десинхронизация (`core/desync/`)

### 4.1 StrategyResolver

Для каждого потока (протокол, порт назначения, resolved-хост) выбирается
стратегия:

1. Правила `rules` проверяются по порядку. Правило участвует, только если его
   маска портов для **этого протокола** непустая — иначе UDP-only правило
   срабатывало бы и на TCP.
2. Внутри правила проверяется источник хостов (`ANY / HOSTLIST / GENERAL /
   GOOGLE / DISCORD / INLINE`) и исключения.
3. Если ни одно правило не подошло — общая стратегия из `AppConfig.toStrategy()`.

Результат кэшируется; отдельно ведётся `ReverseHostCache` (IP → хост) для
случаев, когда DNS-ответ был получен не через нас.

### 4.2 DesyncEngine

`plan(payload, FlowContext(dstPort, knownHost, v6), strategy) → DesyncPlan(writes, applied, technique, host)`

`writes` — список байтовых фрагментов в том порядке, в каком их нужно записать
в upstream-сокет. Варианты:

| Режим | Что делает |
|---|---|
| `NONE` | один `write`, поток прозрачный |
| `SPLIT` | два `write` в выбранной точке |
| `MULTISPLIT` | N+1 `write` по всем выбранным точкам |
| `TLSREC` | ClientHello переупаковывается в N TLS-записей (`Tls.repackRecords`) |
| `MULTISPLIT_TLSREC` | переупаковка + разбиение |
| `HOSTFAKESPLIT` | для HTTP/80: разбиение вокруг значения заголовка `Host:` |

Между фрагментами выдерживается `splitDelayMs`. По умолчанию 0; при
`tcp_autocorking` в Linux две быстрые записи могут склеиться в один сегмент,
тогда помогает 1–2 мс.

Занижать `SO_SNDBUF` меньше одного сегмента бессмысленно: Linux ограничивает
его снизу `SOCK_MIN_SNDBUF` (~4,6 КБ), поэтому разделением управляет только
`TCP_NODELAY` + явная пауза.

### 4.3 Точки разбиения

`Tls.parseClientHello` возвращает `ClientHelloInfo(sni, sniStart, sniEnd, recordLength)`:

| Токен zapret | Смещение |
|---|---|
| `1` | первый байт payload |
| `midsld` | середина домена второго уровня внутри SNI |
| `sniend` | сразу за концом SNI |
| `middle` | середина TLS-записи |
| `custom` | `splitCustomPos` (1–1500) |

`cutoffChunks` ограничивает число обрабатываемых чанков — после него поток
идёт прозрачно (аналог `--dpi-desync-cutoff`).

## 5. DNS (`core/dns/`)

Три слоя:

1. **DnsHandler** — перехват на уровне TUN. Если `dnsHijack`, забираются все
   пакеты на порт 53; иначе только идущие на виртуальные DNS-адреса туннеля.
   Не-A/AAAA-запросы (MX, SRV, PTR, TXT) пробрасываются байт-в-байт через
   `forwardQueryBytes` на первый настроенный сервер.
2. **hosts** — таблица из `lists/hosts.txt` применяется **до** любого резолвера.
   Формат системного `/etc/hosts`; `0.0.0.0` трактуется как блок-лист, и
   соединение до такого адреса не открывается. Это и есть «изменение hosts
   в подключении»: перенаправление домена без root и без правки системных файлов.
3. **DnsResolver** — режимы SYSTEM / CUSTOM / DOH / DOT.
   - `dnsFakeProtection = true`: запрос всегда идёт через настроенный резолвер,
     адрес из самого пакета игнорируется (защита от подмены провайдером).
   - `false`: `forwardRaw()` прозрачно отправляет запрос туда, куда хотело приложение.
   - Блокированные домены получают `buildEmptyResponse(query, rcode = 3)` (NXDOMAIN).
   - Кэш с настраиваемым TTL.

**DoH без OkHttp.** Любой HTTP-клиент пошёл бы через наш же туннель и
зациклился. Поэтому DoH построен вручную: защищённый `SSLSocket`, рукописный
HTTP/1.1, декодирование `chunked`. DoT — то же поверх порта 853.

## 6. UDP (`core/stack/UdpStack.kt`)

- Собственный `ThreadPoolExecutor(2, 192, 30 s, SynchronousQueue)` и свой scope,
  чтобы жизненный цикл не зависел от отменяемого scope туннеля.
- `UdpSession` хранит адрес клиента и защищённый `DatagramSocket` наружу.
- `MAX_SESSIONS = 256` — при превышении новые сессии отклоняются.
- `udpTimeoutSec` — неактивные сессии закрываются.
- **QUIC.** Длинный заголовок QUIC на UDP/443 распознаётся и дропается при
  `blockQuic = true`: клиент тогда падает обратно на TCP, где работает стратегия.
- Режимы: `RELAY` / `BLOCK_FILTERED` / `BLOCK_ALL`.

## 7. Конфигурация (`data/`)

- `AppConfig` — один JSON-документ в DataStore Preferences. `toJson()`/`fromJson()`
  написаны вручную на `org.json`, чтобы не тянуть Moshi/kotlinx.serialization.
  Неизвестные поля игнорируются, отсутствующие берутся из `AppConfig()` —
  конфигурация переживает добавление новых настроек.
- `ConfigRepository.current` — `@Volatile`-снимок для потоков туннеля (чтение
  без suspend); `config: StateFlow` — для UI (`stateIn(Eagerly)`).
- `HostListStore` — пять файлов в `filesDir/lists/`, `Snapshot` с `texts` и
  `count(kind)`, `loadBlocking()` при старте приложения.
- `Presets` — профили YOUTUBE / DISCORD / COMBINED / MAX. Порты и списки взяты
  из реальных `.bat`-файлов upstream-проектов:
  - TLS: `443,8443,2053,2082,2083,2086,2087,2095,2096`
  - HTTP: `80,8080`
  - Discord UDP: `19294-19344,50000-50100,3478-3482`
  - Discord media TCP: `2053,2083,2087,2096,8443` + `--hostlist-domains=discord.media`

## 8. Парсер аргументов zapret (`config/ZapretArgsParser.kt`)

Две функции:

- `parse(text, base): ParseResult` — разбирает строку `.bat`-файла. `--new`
  начинает новое правило; флаги до первого `--new` попадают в общую стратегию.
  Результат разделён на `rules`, поля общей стратегии и четыре диагностических
  списка: `supported`, `ignored`, `unknown`, `errors`.
- `generate(cfg): String` — обратная операция, печатает текущую конфигурацию
  в синтаксисе zapret.

`ROOT_ONLY` — карта флагов, требующих raw-сокетов, с русским объяснением
причины. Они попадают в `ignored`, а не в `unknown`, чтобы пользователь видел
разницу между «не поддержано принципиально» и «опечатка».

Собственные расширения, которых нет в zapret: `--split-delay=N` и `--rule-name=…`.

## 9. UI (`ui/`)

- **Material You.** `dynamicLightColorScheme`/`dynamicDarkColorScheme` на
  Android 12+; на более старых — схемы, сгенерированные через HSV из
  `accentHue(accent)` для шести палитр. Светлая/тёмная/системная тема.
- Навигация: нижняя панель из четырёх пунктов (Главная · Профили · Стратегия ·
  Ещё) + хаб «Ещё» со списками, DNS, сетью, аргументами, журналом, настройками
  и разделом «О программе».
- Внешний `Scaffold` создаётся с `contentWindowInsets = WindowInsets(0, 0, 0, 0)`,
  потому что каждый вложенный экран имеет собственный `Scaffold` + `TopAppBar`.
- Главная: анимированный «циферблат» питания (радиальный градиент, пульсация,
  spring-масштаб), шесть плиток статистики, кликабельная карточка профиля,
  список последних соединений, чек-лист готовности (уведомления / батарея /
  Always-on VPN), баннер про отсутствие root.
- Редакторы списков и правил — полноэкранные состояния внутри своего экрана
  (ранний `return` из composable), а не диалоги: так проще с прокруткой и IME.

## 10. Что не работает без root и почему

| Техника | Причина |
|---|---|
| `fake` (внутри потока) | нельзя вставить пакет в чужой TCP-поток — seq задаёт ядро |
| `disorder`, `multidisorder` | требуется менять порядок сегментов на IP-уровне |
| `syndata`, `synack` | синтез TCP-пакетов вне стека |
| `split-seqovl`, `fakedsplit`, `fakeddisorder` | подделка sequence-номеров |
| `rst`, `rstack` | отправка пакетов вне потока |
| `ipfrag1/2`, `hopbyhop`, `destopt` | манипуляции IP-заголовком |
| `fooling=ts,md5sig,badseq,badsum` | правка TCP-опций |
| `autottl`, `--dpi-desync-ttl` | TTL выставляет ядро |
| `--ip-id` | IP ID выставляет ядро |

Отдельно: идея «обманного» соединения с заниженным TTL (`Os.socket` + `IP_TTL`)
**не работает**. Если TTL меньше длины пути, TCP-рукопожатие не завершается,
значит ClientHello с SNI вообще не будет передан — фильтру нечего сопоставлять.
Поэтому вместо неё реализованы честные цепочки правил `--new`.

## 11. Производительность и надёжность

- Один читающий поток `zapret-tun-reader` (приоритет NORM+2, буфер 32767).
  Всё остальное расходится по пулам TCP/UDP.
- Backpressure с обеих сторон: очередь отправки ограничена `sendBufferKb`,
  приём — 1 МБ с zero-window, число соединений — `maxConnections`.
- Все системные вызовы, способные бросить исключение (`connect`, `protect`,
  `setSoTimeout`, IPv6-настройка), обёрнуты в try/catch: падение одного
  соединения не должно ронять туннель.
- `LogManager` — кольцевой буфер на 1200 записей, публикация в UI не чаще
  раза в 250 мс, чтобы частые записи не дёргали recomposition.
- `SocketProtector` — интерфейс, чтобы DNS можно было проверять из ViewModel
  без запущенного сервиса (реализация `DirectProtector` ничего не защищает).

## 12. Точки расширения

- **Новый профиль** — добавить `ProfileId` + ветку в `Presets.apply`.
- **Новая техника разбиения** — добавить значение в `DesyncMode` и ветку в
  `DesyncEngine.plan`; парсер и генератор подхватят токен автоматически.
- **Новый DNS-транспорт** — реализовать метод в `DnsResolver` и значение `DnsMode`.
- **Новый список** — значение `HostListStore.Kind` с именем файла; вкладка в
  `ListsScreen` добавляется одной строкой в `kinds`.
